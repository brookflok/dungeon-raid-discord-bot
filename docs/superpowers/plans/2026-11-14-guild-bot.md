# Guild Bot for WoW Forever Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Discord bot for one WoW Forever guild with a dungeon finder, raid finder, event planner and character profiles, built so new features are new modules.

**Architecture:** One TypeScript program in layers. `src/core` holds all rules and knows nothing about Discord, SQLite or HTTP; it talks to the outside through the interfaces in `src/core/ports.ts`. Feature modules in `src/modules` plug into a registry and call the core; `src/discord`, `src/storage`, `src/web` and `src/blizzard` are thin outer layers. Core methods return a list of *effects* (filled, promoted, reminder…) that the Discord layer turns into posts, threads and messages.

**Tech Stack:** Node.js ≥ 24, TypeScript (strict, ESM), discord.js 14, better-sqlite3, luxon, zod, Vitest, ESLint + Prettier, Docker, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-14-guild-bot-design.md` — read it before any task.

## Global Constraints

- Dependencies point inward: nothing in `src/core` imports from `discord.js`, `better-sqlite3`, `node:http`, or any other `src/` folder. A module in `src/modules` never imports another module.
- Documentation first: Task 1 (req42 + arc42) is completed before any product code. Every later task that adds a feature ticks its backlog item in `docs/requirements/` and, if it adds a building block, updates section 5 of `docs/architecture/arc42.md`.
- Test-first for everything in `src/core`, `src/storage`, `src/blizzard`, `src/web`: failing test, then code.
- English only. All user-facing text is English; no translation layer.
- Roles are exactly `tank`, `healer`, `dps`, `participant`. Kinds are exactly `dungeon`, `raid`, `event`.
- Defaults from the spec, verbatim: reminders dungeon `[15]`, raid `[1440, 60]`, event `[60]` (minutes before); ASAP expiry 2 hours; flexible expiry 7 days; finished = start + 3 hours, or filled + 3 hours when there is no time; scheduler tick 30 seconds; reminders more than 10 minutes overdue are skipped; link tokens valid 10 minutes, single use; default timezone `Europe/Berlin`; default Blizzard region `eu`.
- Battle.net access tokens are never written to storage or logs.
- Secrets only via environment variables. `.env` is git-ignored; `.env.example` lists every variable without values.
- Errors a member should see are thrown as `UserError` (Task 3) and shown as a private reply; anything else is logged and shown as "Something went wrong."
- Every interaction is acknowledged (`deferReply`/`deferUpdate`) before any storage or network work.

## Review Focus

1. **Two members click the last free slot at the same moment** → exactly one is confirmed, the other is waitlisted; the slot is never overfilled. (Test in Task 5.)
2. **A button is clicked on a post whose activity is finished, cancelled or expired** (stale post, failed edit) → private reply "This group is closed.", no state change. (Test in Task 5.)
3. **A typed time is unparseable or in the past** → `UserError` with an example of a valid input; nothing is posted. (Tests in Task 3 and Task 5.)
4. **The bot restarts with jobs overdue** → overdue expiry/finish jobs run; reminders over 10 minutes late are dropped, not sent late. (Test in Task 6.)
5. **A link token is reused, expired, or the Battle.net account already belongs to another member** → clear error page, no profile change. (Tests in Task 7 and Task 12.)

Also expected of the Discord layer (manual checklist, Task 13): a blocked direct message, a deleted thread or a deleted post never crashes the bot or blocks the other members' notifications.

Rules (spec §5.1, §5.3–5.5):
- All mutating methods run one at a time through a single in-process promise queue inside the service, so concurrent calls cannot interleave.
- `create`: `raid` requires `time.type === 'at'`; a time in the past → `UserError('That time is in the past. Try "today 20:30" or "2026-11-20 19:00".')`; `dungeon` requires `starterRole` and signs the starter up as confirmed.

- One signup per member per activity; a new choice replaces the old one (keeping nothing of the old slot) and may trigger a promotion for the vacated role.
- Role with free capacity → `confirmed`; otherwise `waitlist`. `null` capacity never fills.
- When a confirmed member leaves or moves, the earliest waitlisted member of that role becomes `confirmed` → effect `promoted`.
- State is `full` when every slot with a numeric count has that many confirmed signups and at least one slot is numeric; first transition sets `filledAt` and emits `filled`, later transitions emit `refilled`. Falling below goes back to `open`.
- Dungeon only: when the starter leaves, the earliest confirmed member becomes starter (`starterChanged`); if no signups remain the activity becomes `expired` with effect `closed/empty`.
- `leave` by a member with no signup → `UserError('You are not signed up.')`.

export class Scheduler {
  constructor(deps: { storage: Storage; clock: Clock; activities: ActivityService;
                      onResult: (r: ActivityResult) => Promise<void>; intervalMs?: number }); // default 30_000
  tick(): Promise<void>;       // runs every due job once, deletes it, isolates failures per job
  start(): void;  stop(): void; // start() ticks immediately, then on the interval

`planJobs` rules, for states `open`/`full` only (otherwise `[]`):
- `time.at`: one `reminder` per offset at `at − offset` (omitted if already past), one `finish` at `at + 3h`.
- `asap`: `expire` at `createdAt + 2h` while `open`; `finish` at `filledAt + 3h` while `full`.
- `flexible`: `expire` at `createdAt + 7d` while `open`; `finish` at `filledAt + 3h` while `full`.
Every mutating `ActivityService` method (including Task 5's) ends with `storage.replaceJobs(id, planJobs(activity, now))`.

`runJob` rules: unknown or closed activity → `null`. `reminder` → `null` if more than 10 minutes overdue or no confirmed/tentative signups; else effect `reminder` with `minutesBefore` = the offset. `expire` → only if still `open`: state `expired`, effect `closed/expired`. `finish` → state `finished`, effect `closed/finished`.
`cancel` / `setTime`: allowed for the starter or an officer, else `UserError('Only the starter or an officer can do that.')`; closed activity → `UserError('This group is closed.')`; `setTime` applies the same past-time and raid-needs-time rules as `create`; effects `cancelled` / `timeChanged`.
